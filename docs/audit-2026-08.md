# Launch audit — August 2026

This is the final quality pass before bloomingtonvelo.org goes live as a static site (Task 14
of the rebuild). It picks up from `6812680`, which already fixed the mobile-nav flash (an
inline `.js-nav` script gated by CSP hash), added `<main tabindex="-1">` so the skip link
really moves focus, added a `:focus-within` outline for the cross-origin iframe embeds, and
disclosed the `s.w.org` emoji-icon loads in the privacy policy. None of that is repeated here.

Covers all nine shipped pages: `/`, `/team/`, `/ride/`, `/ride/calendar/`, `/ride/routes/`,
`/sponsors/`, `/contact/`, `/privacy-policy/`, `/404.html`.

**Methodology note:** the "images" column sums *every* URL the page's markup names, including
both sides of each `<picture>` (WebP source + JPEG/PNG fallback) and every breakpoint in a
`srcset`. A real visitor's browser fetches exactly one `<picture>` source and one `srcset`
candidate, so actual transferred bytes are well below this figure — it's a declared-asset
ceiling, not a per-visit measurement. Concretely:

- **`/` (2,175.9 KB referenced):** driven entirely by the hero photo shipped at four
  breakpoints (800/1200/1600/2400px) in both WebP and JPEG. A phone gets `hero-800.webp`
  (~74 KB); a 4K desktop gets `hero-2400.webp` (~506 KB). A typical single visit — smallest
  hero variant plus the shared CSS/JS and header logo — is closer to **~146 KB**, and the
  heaviest realistic single visit (largest hero variant, no WebP support) is **~700 KB**. This
  is the intended shape of a responsive `<picture>`: declaring more bytes than any one visitor
  downloads is the point, not a defect.
- **`/team/` (2,751.6 KB referenced, heaviest page — expected):** 13 roster photos, each a
  `<picture>` with WebP + JPEG/JPG fallback, all `loading="lazy"` below the fold. A
  WebP-capable visit (essentially everyone in 2026) downloads only the WebP side: **~443 KB**
  total including HTML, shared assets, and the header logo — a small fraction of the
  referenced ceiling. This page being heaviest was called out as expected going in, and it is.

**Flagged, not fixed:** several of the roster source photos are much higher resolution than
their ~136px display width — e.g. `Jim-Kirkham-Photo-scaled.jpeg` is 1600×2133,
`JOEL-MCKAY-PHOTO-scaled.jpg` is 1600×2062, `Brian-Drummy-Photo.jpg` is 1333×2000 — because
they're carried over at whatever resolution the club submitted. This inflates `/team/`'s
referenced-byte ceiling and would show up as a Lighthouse "properly size images" opportunity
if that page weren't otherwise scoring 100 across the board (it is — see §2). Per this task's
brief, images are not to be degraded or recompressed to chase a number, so these ship as-is;
if the club ever resupplies right-sized headshots this would shrink for free.

`assets/img/logo.png` (26.5 KB, the header logo) is the one asset every page pays for; it's
small and cached for a year after first load, so not worth chasing either.

### Why `/ride/calendar/` can't reach 95

Chrome's own Issues panel flags two things on that page, both traced to the embedded Google
Calendar iframe itself, not to anything this site serves:

- **`third-party-cookies` (score 0):** Google's calendar iframe sets its own `NID` cookie on
  `calendar.google.com`. That's Google's cookie, set from Google's origin, inside the `<iframe
  src="https://calendar.google.com/calendar/embed?...">` this page intentionally embeds. There
  is no first-party header or markup change that stops Google's own document from setting its
  own cookie.
- **`inspector-issues` (score 0):** the same cookie plus two script loads
  (`apis.google.com/js/api.js` and a `gapi.loaded_*` bootstrap) that Google's embed pulls in on
  its own, all inside that iframe's own browsing context.

Both audits are binary (any occurrence = 0), so a single third-party cookie sets the ceiling
regardless of anything else on the page — every other Best Practices audit passes. The only
way to raise this score is to stop embedding the club's Google Calendar, which would defeat
the page's purpose. This is a legitimate, permanent ceiling, not a local-serving artifact — it
will reproduce identically once the page is live on `bloomingtonvelo.org`.

The same pattern, at smaller scale, is why `/` and `/ride/` sit at 96 rather than 100: the
Strava club-rides widget (`<iframe src="https://www.strava.com/clubs/...">`) sets its own
third-party cookie and carries an `unload` handler inside its own sub-frame
(`UnloadHandlerExistsInSubFrame`, which blocks back/forward-cache restoration). Both are
Strava's script running inside their own iframe document; 96 is still comfortably above the
95 target, so nothing was changed here.

### Expected local false positives (per the brief, not fixed)

- **Missing security headers.** `npx serve .` does not read `.htaccess`, so Lighthouse
  correctly reports no CSP/`X-Content-Type-Options`/`Referrer-Policy`/`Permissions-Policy`
  headers on every page when served this way. `.htaccess` (committed, see Task 13) supplies
  all of these; verifying they actually reach the browser on staging is Task 15's job, not
  something a local `serve` process can demonstrate either way.
- **Strava widget console error.** The brief flagged a `jQuery is not defined` error thrown by
  Strava's own widget script, reproduced standalone against the widget in isolation. Re-running
  that same standalone check today (loading the widget's iframe URL directly in headless
  Chromium and capturing console/page errors) did not reproduce it — no console output at all —
  and it did not appear in any of the 18 Lighthouse runs' `errors-in-console` audit either (all
  scored 1, zero items). Recorded as previously confirmed and possibly intermittent or since
  patched upstream by Strava; either way it is unambiguously their script, not this site's.

### What was fixed

Nothing needed fixing to clear the 95 bar — every category on every page was already at or
above it before this task started measuring. The one sub-95 result (`/ride/calendar/` Best
Practices) is explained above rather than "fixed," because the only fix is removing the
feature.

## 3. HTML validation (W3C Nu validator)

All nine pages submitted to `https://validator.w3.org/nu/?out=json`.

**Eight of nine came back clean** (zero errors; a handful of `info`-level notices, see below).

**One genuine error, fixed:** `/ride/routes/index.html` had an outer `<section class="section">`
(line 69) that wrapped four `<section class="route-group" ...>` children — each with its own
`<h2>` — but carried no heading of its own. The validator's "Section lacks heading" check
flagged it. Fixed by changing that one wrapper element from `<section>` to `<div>` (it was a
pure layout wrapper; `.section` is a CSS class, not a tag-name selector, so styling is
unaffected — confirmed by re-validating, which now returns `clean`, and re-running Lighthouse
on that page, which is unchanged at 100/100/100/100 desktop and mobile).

**Known, deliberately unfixed:** `/team/index.html` reports three instances of *"An `img`
element with a `role` attribute must not have an `alt` attribute whose value is the empty
string"* at line 97, inside Maarten Bout's roster bio (`role="img"` WordPress core-emoji
`<img>` tags for the flag emoji in his bio text). This markup is verbatim, byte-exact
WordPress bio content per the project's standing instruction not to edit bios — the same
content whose `s.w.org` image loads are already disclosed in the privacy policy. Not fixed,
per that instruction; every other line of `/team/` outside `roster-card__bio` blocks
validates clean.

**Info-level, non-error notices, left as-is (all third-party embed markup):**

- `allowtransparency`, `frameborder`, `scrolling` are "obsolete, use CSS instead" on the
  Strava (`/`, `/ride/`) and Google Calendar (`/ride/calendar/`) `<iframe>` embeds. These are
  attributes this site's own markup sets (not carried-over bio content), but they're part of
  each provider's standard embed snippet for cross-browser scrollbar/border suppression, the
  validator reports them as `info`/`warning` rather than `error`, and swapping them for CSS
  equivalents purely to satisfy the linter risks changing rendering inside providers'
  documents we don't control. Left alone.

## 4. Accessibility, by hand

Automated with a small Playwright script driving headless Chromium (same binary Lighthouse
used) rather than a human clicking through nine pages nine times, since the checks the brief
lists are all mechanically verifiable: focus target/order, ARIA state changes, viewport
overflow, and `alt` presence. Every page was loaded fresh for each check.

- **Skip link is the first tab stop and moves focus into `<main>`.** Confirmed on all nine
  pages: the first `Tab` lands on `.skip-link` ("Skip to content", `href="#main"`), and
  activating it moves `document.activeElement` to `<main id="main">`. The `tabindex="-1"` add
  from the prior task is doing its job — without it the `#main` fragment jump would scroll the
  page but leave focus on `<body>`.
- **Focus visible at every stop; order follows visual order.** Tabbed through the full page
  (up to 40 stops) on all nine pages. The only elements with no visible browser-default outline
  were the third-party `<iframe>` embeds themselves (Strava/Google Calendar) — expected, and
  already covered by the `.embed:focus-within` outline added in the prior task, which fires on
  the wrapping `<div class="embed">` the instant the iframe inside it holds focus (confirmed
  present in `assets/css/site.css`, verified by inspecting the rule directly). No non-embed
  element on any page lacked a focus indicator. Tab order matched visual/DOM order everywhere
  (header → nav → main content → footer), since nothing on the site uses a manual `tabindex`
  other than the one `-1` on `<main>`.
- **At 390px, the nav toggle opens/closes and Escape returns focus to the button.** Verified on
  all nine pages at a 390×800 viewport: clicking `.nav-toggle` sets `aria-expanded="true"` and
  `#site-nav[data-open="true"]`; pressing `Escape` sets `aria-expanded="false"` again and moves
  focus back to `.nav-toggle` (matches the `keydown` handler in `assets/js/nav.js`, which does
  exactly this and nothing else — no focus trap, so it doesn't try to hold focus inside the
  nav, which is correct for a menu this small).
- **With JavaScript disabled, the nav is fully usable.** Checked `/` and `/team/` in a
  Playwright context with `javaScriptEnabled: false`. Since the `.js-nav` class is added by the
  inline `<head>` script and nothing else ever collapses `#site-nav`, with JS off `#site-nav` is
  visible (`display` is not `none`) and `.nav-toggle` stays hidden (`display: none` is the
  unconditional default in `assets/css/site.css`; only `.js-nav .nav-toggle` shows it). This is
  the progressive-enhancement design already documented in `nav.js`'s own comment — confirmed
  it actually behaves that way rather than just being commented that way.
- **200% zoom: no horizontal scroll, no clipped text.** Simulated via `document.body.style.zoom
  = '2'` at a 1280×900 base viewport (equivalent to an effective 640×450 logical viewport) on
  all nine pages. `document.documentElement.scrollWidth` never exceeded `clientWidth` on any
  page — no horizontal scrollbar induced on any page.
- **Every `alt` describes its image; decorative images use `alt=""`.** Extracted every `<img>`
  on all nine pages: zero images are missing the `alt` attribute outright. The `alt=""` cases
  are exactly the ones that should be empty — the header brand logo next to visible "Bloomington
  Velo" text on every page, and the WordPress core-emoji flag icons inside Maarten Bout's
  verbatim bio (decorative glyphs inside running text, correctly `alt=""` even though the
  `role="img"` combination trips the Nu validator's stricter rule — see §3). Every roster photo
  on `/team/` carries the person's name as `alt` (e.g. `alt="Taylor Allen"`), which is the
  accepted pattern for identifying a headshot; the sponsor logo on `/sponsors/` reads `alt="Dumonde
  Tech"`; the homepage/ride-page hero photo reads `alt="Bloomington Velo riders gathered at the
  Indiana University Sample Gates"`, a real description rather than a filename or generic label.

No accessibility defects were found by hand that Lighthouse's automated pass (100/100 on
accessibility, every page, both viewports) didn't already imply.
